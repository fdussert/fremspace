# Spaces spike (plan 1, Task 0)

Date: 2026-11-08. macOS 27.0.1 (26A434), SIP untouched. Throwaway code in `~/spikes/fremspace-spaces/`
(not committed): `spaces.swift` (read-only dump), `move.swift` (direct CGS move), `app.swift` (a small
signed `.app` holding Accessibility, for focus and drag).

Displays at the time of the spike: built-in Retina (1512×982 pt), two DELL S3221QSA 32" 4K
(3360×1890 pt each, same vendor 4268 and model 53511, distinct serials), XENEON EDGE (2560×720 pt,
serial 16843009 = `0x01010101`, a placeholder). "Displays have separate Spaces" is on
(`spans-displays = 0`).

## Summary

| Step | Technique | Result |
|------|-----------|--------|
| 1 | Read Spaces with `CGSCopyManagedDisplaySpaces` / `CGSCopySpacesForWindows` | **Works.** Every display, every Space, the current one, and the Space of every window. |
| 2 | Focus a window on another Space | **Works, 19/20** with either activation method; ~450 ms including the Space slide. Needs the "remote token" AX trick to even find the window. |
| 3 | `CGSMoveWindowsToManagedSpace`, `CGSAddWindowsToSpaces` / `CGSRemoveWindowsFromSpaces` | **Ignored.** No error, no effect (as expected without SIP changes). |
| 4 | Simulated title-bar drag + `⌃→` (Amethyst style) | **Does not work: 1/25.** The window is not even dragged by synthetic mouse events. |
| 5 | Dock "Assign to desktop" bindings (`com.apple.spaces app-bindings`) | **Does not place windows.** The app's activation switches the display to the bound Space, but the window opens on the Space that was current at launch. |
| 6 | SkyLight bridged operation `SLSBridgedMoveWindowsToManagedSpaceOperation` (2026-11-09) | **Works: 43/44**, under 0.1 s, SIP on, Finder and Brave windows, across displays and within one display. See step 6; it changes the plan 3 recommendation. |

Steps 3–5 do not reach 19/20; step 6 (added 2026-11-09) does. Recommendation at the end.

## Step 1: reading Spaces

- `CGSMainConnectionID` + `CGSCopyManagedDisplaySpaces` returns one entry per display: `Display Identifier`
  (the display UUID, same as `CGDisplayCreateUUIDFromDisplayID`), `Current Space`, and the ordered
  `Spaces`, each with `ManagedSpaceID`, `uuid` and `type`. `type == 0` is a normal desktop,
  `type == 4` a native full-screen Space. The first desktop of the main display has an empty `uuid`.
- `CGSCopySpacesForWindows(cid, 0x7, [wid])` returns the Space ids of a window. Windows that are
  minimized, hidden or ordered out return `[]`.
- Output matched the layout at the time (left DELL: desktop 1 + Orca full screen; built-in: desktop
  1 + two full-screen Spaces). After the owner added a desktop in Mission Control it showed up at once,
  at the right index.
- No permission needed for this part. Window titles came through because the terminal already had
  Screen Recording; without it `kCGWindowName` is empty (titles must come from AX instead).
- Index caveat: full-screen Spaces sit in the same ordered list as desktops. Configured Spaces map to
  real Spaces "by position" (spec), so plan 1 counts **only `type == 0` desktops** when computing a
  Space index.
- **`killall Dock` reorders Spaces:** after it, the left display went from `[desktop, full screen,
  desktop]` to `[desktop, desktop, full screen]`. Full-screen Spaces move to the end. Another reason to
  index desktops only.

## Step 2: focusing a window on another Space

Target: a Brave window on the left display's desktop 1 while Orca was full screen on the same display,
then back to Orca. 10 round trips per method (20 focus operations each).

- **Finding the window is the hard part.** `kAXWindowsAttribute` only lists a process's windows on
  the *current* Space. Windows on other Spaces are reachable only by brute-forcing
  `_AXUIElementCreateWithRemoteToken` (pid + `"coco"` magic + element id, ids 0..<1000), the technique
  alt-tab-macos uses. It found the target every time, in ~50 ms.
- Method A, public: `kAXRaiseAction` + `kAXMain = true` + `NSRunningApplication.activate()`:
  **19/20**, 520–550 ms. The failure: Brave came forward but with its *other* window (on another display).
- Method B, private: `_SLPSSetFrontProcessWithOptions(psn, wid, 0x200)` + the two `SLPSPostEventRecordTo`
  key-window records + `kAXRaiseAction`: **19/20**, 420–500 ms. The failure: once, going back to the
  full-screen Orca window.
- Both methods switch the display to the window's Space with the normal slide, then focus it.
- For plan 4 (switcher): use method B, check the focused window afterwards (system-wide
  `kAXFocusedApplication` → `kAXFocusedWindow`) and retry once; that should cover the 1/20.
- Measurement trap: `NSWorkspace.frontmostApplication` is stale in a process without a running run
  loop; the first run looked like 0/10 because of it.

## Step 3: direct move APIs

`CGSMoveWindowsToManagedSpace(cid, [wid], target)`, then `CGSAddWindowsToSpaces` +
`CGSRemoveWindowsFromSpaces` on a Finder window: no error, `CGSCopySpacesForWindows` unchanged, nothing
moved on screen. macOS 27 silently ignores them for other apps' windows without SIP changes. Dead end.

## Step 4: simulated title-bar drag

Setup: the owner added a second desktop on the left display, so the order was
`[desktop 1, Orca full screen, desktop 2]`. Mission Control shortcuts `⌃←` / `⌃→` were already on
(`⌃1`…`⌃3` are off). Windows: Finder (grab point in the empty toolbar strip), VS Code (empty title bar
area), Brave (the strip between the new-tab button and the profile button, found through AX). Each trial:
focus the window (step 2 method B), post mouse-down in the grab point, drag events, `⌃→` or `⌃←` twice
(to step over the full-screen Space), mouse-up, read the window's Space.

- **1 success out of 25.** The very first trial (Finder, desktop 1 → desktop 2, ~2 s, two visible
  slides) worked. The 20 trials of the series and 4 diagnostic variants all failed: the Space switched,
  the window stayed.
- Diagnosis: the grab point hit the right window every time (`AXUIElementCopyElementAtPosition`), but
  **the window does not move at all under synthetic drag events**, even 20 pt of drag, with any of:
  a `hidSystemState` event source, `mouseEventClickState = 1`, explicit `mouseEventDeltaX`, a 300 ms
  hold before dragging. WindowServer does not start a window drag from these events, so there is
  nothing for the Space switch to carry. The one success is unexplained.
- Visible effect when it fails: the display slides to the next Space and back on the next trial; the
  mouse pointer jumps to the title bar and back.
- Side effect left behind: Finder's "header" window is now on desktop 2 of the left display (moved by
  the one successful trial).

Not usable as is. It might be revived later (real-time CGEventTap injection, different grab timing,
following how Amethyst behaves on macOS 26+), but nothing in this spike suggests 19/20 is reachable.

## Step 5: Dock bindings

Test app: TextEdit instead of Finder (ruling: binding Finder and relaunching it would have moved all of
the owner's ~10 Finder windows; TextEdit had no windows open, so the test disturbed nothing). Binding:
`defaults write com.apple.spaces app-bindings -dict-add com.apple.textedit <desktop 2 uuid>`, then
`killall Dock`.

- The binding is the documented format (lowercased bundle id → Space uuid) and `defaults read` shows it.
- Launch 1 (left display showing Orca full screen): the window opened on **another display** (the
  right DELL, where TextEdit last had its window).
- Launch 2 (left display showing desktop 2, the bound one): the window opened there. Inconclusive,
  that was also the current Space.
- Launch 3 (left display showing desktop 1): the window opened on **desktop 1**, and right after,
  the display switched to the bound desktop 2, away from the window.
- So the binding drives "which Space to show when the app activates", not "where the window goes".
- Survival across logout: not tested (needs the owner to log out); moot given the above.
- Cleanup done: binding deleted, Dock restarted, Orca focused again. `killall Dock` reorders full-screen
  Spaces (see step 1).

## Step 6: bridged move operation (2026-11-09)

Lead from a research session for the owner (`brief-for-fremspace-agent.md`, yabai 7.1.25, spacetools,
rift #404): since macOS 26.4 SkyLight exposes `SLS*Bridged*Operation` classes that run window
management through the window server's "WM bridge", which works with SIP on. Throwaway code in
`~/spikes/fremspace-bridged/` (`bridged.swift`, a plain command-line tool run from the Orca terminal,
no app bundle). Fremspace was paused during the run; the owner gave the go.

- On 27.0.1 both classes exist: `SLSBridgedMoveWindowsToManagedSpaceOperation`
  (`initWithWindows:spaceID:`, `windows`, `spaceID`, `invokeFallback`; superclass
  `SLSAsynchronousBridgedWindowManagementOperation` adds `performWithWMBridgeDelegate`) and
  `SLSWindowManagementFallbackBridge` (`performAsynchronousBridgedWindowManagementOperation:`,
  `performSynchronousBridgedWindowManagementOperation:`, `performWindowManagementBridgeTransactionUsingBlock:`).
  The C function `SLSPerformAsynchronousBridgedWindowManagementOperation` is not exported (`dlsym` nil).
- Load SkyLight with `dlopen`, build the op through `class_getMethodImplementation` on
  `initWithWindows:spaceID:` (window ids as `NSNumber`, Space as `id64`), then run it one of three ways:
  (a) the brief's snippet: inside `performWindowManagementBridgeTransactionUsingBlock:`, call the bridge's
  `performAsynchronousBridgedWindowManagementOperation:`; (b) the same transaction around
  `[op performWithWMBridgeDelegate]`; (c) `[op performWithWMBridgeDelegate]` alone. Never the synchronous
  variant (reported to trap). Check with `CGSCopySpacesForWindows`, polled every 0.1 s.
- Test window: a fresh Finder window (another process) opened on the right DELL (Space 21).

| Move | Result |
|---|---|
| Very first call, variant (a), right DELL → built-in desktop 2 (hidden) | **No effect** after 1 s and after (not reproduced; cause unknown) |
| Variant (b), same move | moved, < 0.1 s |
| 5 round trips 21 ↔ 134 with each of (a), (b), (c) | **30/30**, each < 0.11 s |
| Built-in desktop 2 → built-in desktop 3 (shown), and back (same display) | moved, < 0.1 s |
| Third-party app: a fresh blank Brave window (owner's go), 5 round trips right DELL ↔ built-in desktop 2, then built-in desktop 3 (shown) and back | **12/12**, each < 0.11 s |

- No display changed its shown desktop during any move; the window simply disappears from one desktop
  and appears on the other.
- **Frame:** within one display the window keeps its frame. Arriving on another display it lands
  mostly off screen (right DELL x = 4909 → built-in x = -880, 40 pt visible), so the caller must place it.
- **AX afterwards:** on the shown desktop AX sees it and sets its position normally. On a hidden desktop AX
  does not list it (only current-Space windows), so it is placed when its desktop is shown — which is
  what the engine already does on a Space change.
- Brave's frame across displays: 2088×1844 at the right DELL's top left → built-in (0, 30), same size
  (larger than the display); back on the right DELL at (4872, 349) instead of (4872, -559). Within
  one display the frame is kept.
- Not tested: full-screen
  Spaces (reported unsupported); the very-first-call failure (a retry with verification covers it).

## Recommendation for plan 3 (restore after login, "send elsewhere")

**Superseded in part by step 6 (2026-11-09):** the bridged move puts an existing window on a chosen
Space with SIP on. If the owner agrees, plan 3 keeps "send elsewhere" and "put this existing window back
on its desktop", using the bridged move (verify with `CGSCopySpacesForWindows`, retry once, then place
the window when its desktop is shown); launching on the right Space stays the fallback for apps that are
not running. The text below is the recommendation as it stood after step 5.

Neither the simulated drag (1/25) nor the Dock bindings place a window on a chosen Space. Per the
spec's fallback, plan 3 should:

1. **Arrange windows on whatever Space they are on.** No cross-Space moves for windows that already
   exist, so no "send elsewhere" in its original form, and no "put this existing window back on
   Space 3".
2. **Restore by launching on the right Space** (new candidate, cheap to verify in plan 3): launch 3
   above shows that a freshly launched app opens its window on the Space current at launch (on the
   display where its window frame lands). At login, for each display and each configured desktop:
   switch to that desktop (focus any window already there, or post the `⌃→` shortcut, which works
   reliably), then launch the apps whose slots live there and wait for their first window; then
   place it in its slot. This covers the spec's "launch the app if it is not running" restore, which
   is the main restore case after a reboot. It does not cover apps that restore several windows on
   several Spaces by themselves (Brave with several windows), and it does not cover Brave profiles
   (one process).
3. **Keep the Space-reading code from step 1 and the focus code from step 2**: both are reliable and
   are what plan 1 (current Space per display) and plan 4 (switcher) need.
4. "Send elsewhere" could degrade to a notification ("this window belongs on Le reste") instead of a
   move. Owner's call.

The owner decides whether to accept this fallback before plan 3 is written.
